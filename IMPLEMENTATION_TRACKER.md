## Product direction

Open email signup. One user account can switch between Rider and Driver. There is no user-facing community, invitation, sponsor, or operator requirement. The database's community/membership structure is retained only as an automatic internal marketplace scope.

- **Route-corridor matching — the product requirement, implemented (migration `0032_route_geometry.sql`, `src/domain/geo.ts`).** The owner's requirement was concrete: a driver going Muridke → Model Town Lahore should match a rider going Rana Town → MAO College because the rider's leg lies *along* the driver's route, with no fixed radius; matching should follow real navigation paths, and live tracking should be on a map. `ROUTE_MATCHING_PLAN.md` holds the design. This is a genuine improvement over area-name matching in **both** directions: a 2 km radius matched a driver going the *opposite* way, and missed a driver on the rider's exact road 30 km along it. What is built: (1) origin/destination coordinates on a commute, plus a `commute_routes` store holding the decoded path with provider/distance/duration; (2) the trip **snapshots** the route at publish time, the same copy-on-publish rule the cost-sharing note follows, so editing a commute cannot change an already-published trip's path; (3) `src/domain/geo.ts` — `projectPointOntoRoute` (perpendicular offset and distance-along, with the segment projection clamped so a point past the route's end measures to the endpoint instead of an imaginary extension) and `matchLegOnRoute`, which requires **both endpoints within a lateral tolerance AND the rider boarding before they alight AND both ends inside the route's own extent AND a non-degenerate leg**; (4) search uses the SQL as the cheap filter (date, time, seats, blocks) and decides the corridor in TypeScript on the small candidate set, ranking by how much of the driver's route the rider is actually on board for. **Every new column is nullable and matching falls back to area names when no map points are given, so nothing that worked before stopped working.** Verified: 18 geometry checks against the Muridke corridor including the product example, the reverse direction (rejected even with a 50 km tolerance, so a false match cannot be widened into existence), off-corridor legs, legs beyond either end, and a zero-length leg; and 7 checks end to end against the live database (snapshot, positive match with a real coverage fraction, reverse rejected, off-corridor rejected, and area matching unchanged when no points are supplied). Provider geometry is currently **synthetic** — the algorithm is real, the test corridor is hand-made — so "follows real navigation" is not yet true until a routing provider is chosen (roadmap §6.2).

- **Phase 1b — ratings (migrations `0030_ratings.sql`, `0031_rating_erasure_on_closure.sql`).** After a completed trip each side rates the other 1–5 with an optional comment, shown on the dashboard under "Ratings about you" and as an aggregate on the counterpart card. Four rules keep the signal honest rather than maximising engagement: **only a `COMPLETED` request is rateable** (a ride that did not happen is not rateable); **one rating per side per request** (a unique index, so nobody can inflate or bury a counterpart by rating repeatedly); **a rating is immutable** — there is no edit or withdraw path, because a rating you can retract once the other side retaliates is a negotiation rather than a record, and a database trigger refuses both; and **nothing acts on a rating automatically** — no suspension, warning or down-ranking, because deciding what a pattern should trigger is a fairness decision (roadmap §4), and storing data is not the same as acting on it. An average is **withheld until three ratings exist** (`MIN_RATINGS_FOR_AVERAGE`): one five-star rating is not a reputation and is not displayed as `5.0`. Verified against the live database (12 checks) and in a browser: refused before completion, by a non-participant, out of range, and twice; the aggregate withholds a single rating; an UPDATE is refused and a direct DELETE is refused, while deleting the ride still cascades so **retention is not blocked**.
- **A bug my own migration introduced, caught before it shipped: the immutability trigger broke account closure.** `0030` blocked every direct `DELETE` on `trip_ratings`, which correctly stops a user withdrawing a rating — and incorrectly stops `deleteOwnAccount`, which must remove a closed person's data. Since the read path joins `users` for the author's name, a surviving rating would have kept a name attached to a tombstone that is supposed to carry none, contradicting the closure promise. Migration `0031` replaces the trigger with a three-case rule: an UPDATE is always refused; a nested delete (a ride being removed by retention) is allowed; and an explicit erasure transaction sets `SET LOCAL app.allow_rating_erasure = 'on'`. The flag is deliberate rather than inferred so every place permitted to erase a rating is findable by search. Verified: closing an account with ratings present now succeeds, erases the ratings it wrote and received, and leaves no rating naming a closed account.
- **A second bug, found in the browser: the rate form was re-offered after submitting.** The dashboard derived "requests I have already rated" from the list of ratings *about* me — the wrong question, since a rating I write appears in the recipient's list. The API now returns `authoredRequestIds` separately, and a rated trip reads "You rated this trip" instead of offering a form the server would refuse.

- **Phase 1a — profile and vehicle identity (migrations `0029_profile_and_vehicle.sql`).** A rider about to get into a stranger's car needs to know who is coming and which car. Adds `users.phone` / `users.phone_verified_at` and a `driver_vehicles` table (make, model, colour, plate, seats; one per driver, enforced by a unique index rather than application logic so a race cannot create two). The privacy rule is the one already used for meeting details: `getCounterpartIdentity` returns the other participant's phone and vehicle **only when the request is `ACCEPTED`** and the caller is a participant, and returns `null` — not an empty object — otherwise, so a caller cannot distinguish "no phone on file" from "not allowed to see it". Verified against the live database (19 checks) and in a real browser, both directions: an accepted request shows the driver's phone and plate to the rider and the rider's phone to the driver (with no vehicle invented for a rider); a **pending** request shows neither (`HAS_PHONE: false`, `HAS_VEHICLE: false`); clearing the phone or removing the vehicle removes it; and cancelling revokes access. Phone normalization keeps a leading `+` for international input and the leading `0` for local input, and stores digits only. Deliberately **not** included: photo upload (needs object storage and a moderation path — a half-built upload with no review is worse than none) and SMS verification (needs a provider and a budget; the column records the number and the verified flag, and an edit clears the flag so a changed number cannot inherit earlier trust).
- Meeting details (migrations `0027_meeting_details.sql`, `0028_meeting_detail_notification_kind.sql`). Areas are deliberately approximate, so once a driver accepts a seat either participant can record a precise pickup point or contact detail (`PUT /api/rides/{requestId}/meeting-detail`), which is what `plan.md` requires: precise information shared "only when needed for an accepted trip and with the parties involved". Each side writes only its own column, so neither can rewrite the other's. The access rule is enforced **in the database, not just the UI**: the read query masks both columns to `NULL` unless the request is `ACCEPTED`, and a `BEFORE INSERT OR UPDATE` trigger clears both columns whenever a request leaves `ACCEPTED`. That single trigger is deliberate — a request leaves `ACCEPTED` from six different statements (driver cancels the trip, rider cancels the request, decline, the expiry sweep, account closure, and reviewer dispute resolution), so a `CHECK` would have rejected all six until each was edited and would have silently started rejecting any seventh. The notice that announces a shared detail carries no detail text, because inbox rows are stored and polled broadly. `health-check` asserts `no meeting detail is retained on a non-accepted request`, so a dropped trigger fails the deployment gate. Verified against the live database (7 checks, self-cleaning): a detail is refused while pending; each side sees the other's detail once accepted; a non-participant is refused and sees no requests; a blank entry withdraws the value; and cancelling clears both columns in the database. Also **verified in a real browser, both directions** (two signed-in sessions, one accepted trip carrying a detail on each side): the rider's request list showed the driver's text under the driver's name plus the rider's own with a withdraw control, and the driver's seat-request list showed the mirror image — neither side saw its own text presented as the other's. Zero console errors and zero failed requests in both sessions. Not encrypted at rest, deliberately — the threat is other users, not the database operator.
- Geographic area matching (migration `0026_area_coordinates.sql`). A reviewer/operator records a coordinate for an area; two areas whose resolved names differ but which both have coordinates within a server-configured radius (default 2 km, `0` disables) now match in search. Distance is compared **only** between areas an operator has explicitly placed — never inferred from a name — and exact/alias equality is evaluated first and unaffected, so an area with no coordinate behaves exactly as before. Managed at `/moderation/reports` alongside aliases; readable by any active member. The radius is server-controlled, not read from the request, so a client cannot widen matching. Search reports **which rule admitted each side** (`originMatch`/`destinationMatch`, `EXACT` or `PROXIMITY`), and the rider dashboard labels a distance match explicitly ("near your pickup area, but not an exact name match — confirm the meeting point") rather than presenting it as a name match. This deliberately supersedes the earlier "areas are never matched by geography" position; see `DECISIONS.md` for why this is not the guess that decision rejected.

Two independent defects:
  1. `resolveTripDispute` read `dispute.request_id` while the query aliased the column as **`ride_request_id`**, so the value was `undefined`, the request `FOR UPDATE` matched nothing, and the function threw `notFound()` before doing anything. Fixed by reading `dispute.ride_request_id` and correcting the row type.
  2. After that fix, the write that moves the request to `COMPLETED` did not set the confirmation flags, so migration `0024`'s `ride_requests_completed_requires_both_confirmations` CHECK rejected it. A reviewer deciding a disputed trip happened is the authority on that fact for both sides; the resolution now sets both confirmation flags when recording `TRIP_CONFIRMED`, and leaves them untouched for `TRIP_NOT_COMPLETED`.
  A third defect surfaced once the second was reached: `resolveTripDispute` writes a `TRIP_DISPUTE_RESOLVED` inbox notice to both participants, but that value was never added to the `notification_kind` enum, so the whole transaction failed at the notification step. Migration `0025` adds the enum value.
- **`npm run verify:dispute` verified a copy of the code, not the code.** The script kept its **own copy** of the resolution SQL ("Mirrors resolveTripDispute … SQL only") and only ever resolved to `TRIP_NOT_COMPLETED` → `EXPIRED`. It called `TRIP_CONFIRMED` exactly once, against a request it had deliberately set back to `ACCEPTED`, expecting `REQUEST_NOT_DISPUTED` — so the `COMPLETED` branch, the branch that was broken, was never executed. Its mirrored SQL had the same missing confirmation flags, and it never inserted a `TRIP_DISPUTE_RESOLVED` notice, so it could not observe the enum gap either. It now **imports and calls the real `resolveTripDispute` / `listOpenTripDisputes`** through an `@/*` alias loader, so there is no copy left to drift (16 checks). The loader (`scripts/lib/alias-loader.mjs` + `register.mjs`) maps `@/x` → `src/x` and is run with `node --experimental-transform-types` (strip-only mode rejects the parameter properties in `errors.ts`). A negative control that removes the production confirmation-flag updates makes the run fail with the live constraint error, so it exercises the code rather than a copy.
- **`npm run health-check` claimed to verify "every notification kind the code writes", but its `EXPECTED_KINDS` was a hand-maintained list** that did not include `TRIP_DISPUTE_RESOLVED`. A hand-written list can only catch a kind someone remembered to add — which is why the check passed while a written-but-unmigrated kind was failing at runtime. It now **derives the kinds by scanning `src/`** for `kind: "…"` literals that are immediately followed by `eventKey:` (the pairing skips same-named unions such as `AccountActivityItem.kind: "TRIP" | "REQUEST"`, which is not a notification kind). It reports 13 kinds present and, as a negative control, a deliberately misspelled kind fails the check by name.
- **The dashboard showed a misleading empty state while the first load was still in flight.** With a slow API round-trip (2–4s in this environment against the remote database), "Your requests", "Your activity", "Your reports", "Your published trips" and "Save a commute first" all read as if the account genuinely had none, so a user with existing data would believe it had vanished. Each list now shows **"Loading…"** until the first load settles (`dashboardLoaded`), and the inbox does the same via `notificationsLoaded`; the empty-state text is only shown once the load has actually completed (including when it failed and set the error). Verified in a browser by sampling the DOM over a fresh load: it shows `Loading…` then the real request, and never falsely claims "No requests yet".
- **Four concurrent accepts on one trip deadlocked in production, and the mirror could not see it.** With `verify-concurrency` converted to call the real `acceptRideRequest`, four riders racing for a one-seat trip produced **three `40P01` deadlock errors** instead of clean `NO_SEATS_AVAILABLE`. Live `pg_locks` sampling during the hang showed the cycle: each transaction held a row lock in `idempotency_records` (its own idempotency key) and then contended on the driver's `account-action` advisory lock, and Postgres resolved the wait-for graph as a deadlock. The previous mirrored test could not observe this because it omitted *both* the advisory lock (`lockUserActions`) and the idempotency insert entirely — it re-implemented only the capacity guard. **Fix:** take the account's advisory lock at the top of the transaction, before `withIdempotency` inserts the idempotency row, so every concurrent operation on the same account shares one lock order (advisory locks first, then rows). The pair-lock call inside `usersAreBlocked` was also moved ahead of the trip row lock in `acceptRideRequest` and `requestSeat`, so an advisory lock is never taken while holding a row lock. Verified: four concurrent accepts now yield exactly one `ACCEPTED` and three `NO_SEATS_AVAILABLE`, stable across repeated runs. A new assertion (`no accept deadlocks under contention`) fails with the exact `40P01` codes when the fix is reverted, so the regression is covered by name.
- **Three more verification scripts now call the real code instead of a mirror.** `verify-no-show` (9 checks) imports the real `expireStaleTrips` sweep; `verify-notifications` (10 checks) imports the real `listNotifications`/`markNotificationRead`/`markAllNotificationsRead`; `verify-concurrency` (9 checks) imports the real `acceptRideRequest`/`cancelTripOccurrence`. Each was proven non-vacuous by a negative control that breaks the real function and observes the failure. `verify-no-show` was also made self-contained (own accounts) and cleans orphans from interrupted runs. The `@/*` alias loader gained resolution for extensionless relative imports (`./errors`), which the server sources use and Node's ESM resolver rejects.

- **Trip completion implemented and verified.** Both sides confirm independently; the request completes only when both confirm, and settles to `EXPIRED` if the `completion_window` lapses first. Disputes are recorded in `trip_disputes` and move the request to `DISPUTED`. A request that was never accepted and whose trip has departed is expired rather than left showing an "Accept" control the server will refuse.
- **Capacity-settlement bug found and fixed.** Closing a trip (via confirmation or the expiry sweep) set the status but never released `seats_reserved`, so a finished trip permanently held seats that no request accounted for. That breaks the invariant overbooking protection relies on. Migration `0011` backfills already-closed trips.
- **No-show evidence implemented and verified.** When a completion window lapses, the sweep records which side had confirmed (`RIDER_UNCONFIRMED`, `DRIVER_UNCONFIRMED`, `NEITHER_CONFIRMED`) in `trip_no_show_evidence`, preserving the flags as they stood at expiry. Reviewers see it at `/moderation/reports` under "Unconfirmed trips". It is evidence for a human, never an automatic penalty.
- **In-app notifications implemented.** Seat requests, accept/decline/cancel, trip cancellations, completion confirmations/completion, expiry, disputes, and new safety reports create recipient-scoped inbox entries in the same transaction as the state change. Safety reports notify active operators/reviewers in the internal scope. Stable unique event keys prevent duplicate entries; recipients control read state. The dashboard refreshes on load/action/focus and polls every 30 seconds while visible.
- **Duplicate expiry sweep removed.** `requests.ts` carried its own copy of the sweep, which had drifted: it closed trips without settling capacity and recorded no evidence. It now delegates to the single canonical implementation in `completion.ts`, so the read path cannot diverge again.
- **Trip lock order unified for expiry.** The completion sweep now locks due parent trips in ascending ID order before changing requests, in bounded `SKIP LOCKED` batches of 25. This matches acceptance/cancellation/account-closure lock ordering and avoids concurrent sweepers blocking on the same batch.
- `npm run verify:integrity` is a read-only cross-table integrity check (21 checks) covering the areas added since completion verification: disputes (community match, an open dispute matches a `DISPUTED` request, resolution fields consistent), notifications (recipient/community exist, never addressed to its own actor), safety reports (community match, participants are members, latest audit event matches current status, closed reports are assigned), cost sharing (a published trip never carries a note its unedited commute never had), **area aliases** (community exists, no self-alias, keys are normalized, no cycle), account closure (no live auth subject, no real display name, no ACTIVE membership, no open request), and memberships. Writing it twice exposed **two vacuous checks** (blank/over-long notes, and a blank stored support contact) that could never fire because the schema already forbids those rows; both were removed rather than left to look like coverage. Negative controls confirmed the remaining injected violations (tampered trip note, live auth subject on a closed account, self-addressed notification, open dispute on a non-disputed request, unnormalized alias, alias cycle) are actually detected.
- `npm run verify:area-alias` exercises area-alias resolution against a real database (9 checks, self-cleaning): two spellings do not match before an alias exists, the alias resolves to its canonical area, an unaliased area resolves to itself, a search by the alias finds the canonical trip and vice versa, case/whitespace are still ignored, a second alias for the same area is rejected, an alias pointing at itself is rejected by the schema, and removing the alias restores exact matching.
- `npm run verify:reviewer-role` runs the real `set-reviewer-role` command as a child process (8 checks, self-cleaning): it promotes an active account, switches a reviewer to `OPERATOR`, demotes to `MEMBER`, and refuses an unknown email, a closed account, an invalid role, and missing arguments, without touching an unrelated account. This test found and fixed a bug that made the command fail unconditionally.
- `npm run verify:contribution` exercises the display-only cost-sharing note against a real database (6 checks, self-cleaning) by **calling the real `createTripOccurrence`** rather than re-implementing its INSERT: the note is copied to a published trip, editing the commute does not rewrite a trip already published while a later publication uses the current note, an absent note is stored as `NULL` rather than an empty string, and the 160-character ceiling is enforced by a schema CHECK. A note is free text — the app parses no amount and handles no money. A negative control that nulls the note copy in production fails three checks.
- **COMPLETED without both confirmations was possible, and two rows existed.** The schema only required `accepted_at IS NOT NULL` for a completed request, so a `COMPLETED` row could carry a single confirmation flag; `completion.ts` even claimed "the DB CHECK enforces ... both flags", which was false. Two rows from 2026-10-08 had `rider_confirmed_completion = false`. Migration `0024` corrects them to `EXPIRED` with `completed_at` cleared — the state a one-sided confirmation should have reached — rather than inventing a confirmation nobody gave, then adds `ride_requests_completed_requires_both_confirmations`. Verified both directions: a one-sided `COMPLETED` is now rejected by the database and a genuine one is accepted. `verify-completion` and `verify-integrity` cover it.
- **Invariant check extended.** `npm run verify:completion` (9 checks) asserts the schema invariants across live data and **imports the real `classifyOutcome`** instead of re-deriving the no-show outcome with its own `CASE` expression. It also inserts a known evidence row so the classifier agreement check is not vacuous on an empty table, and asserts evidence matches its request and outcome, and that settled requests carry no no-show evidence. `npm run verify:no-show` exercises the expiry path end to end (9 checks, including that re-running the sweep never duplicates evidence).
- **Overbooking is defended at two layers, and that is now proven.** `npm run verify:concurrency` fires parallel accepts on a one-seat trip through independent connections: exactly one succeeds, the rest get `NO_SEATS_AVAILABLE`, and `seats_reserved` never exceeds `seat_capacity`. Its negative control removes the application guard on purpose and shows the database `CHECK` still refuses the increment — so the test cannot pass vacuously, and a future removal of the app guard is still caught. A concurrent accept and trip-cancel resolves to a single coherent outcome with no accepted request left on a cancelled trip.

- **Published-trips race fixed.** The dashboard previously issued two overlapping loads; a slow earlier response could overwrite newer data, so a freshly published trip did not appear. The loader is now a single guarded function with a monotonic sequence number, and the initial load is deferred out of the effect body.
- **Area normalization unified.** Template creation previously validated raw length while search validated normalized length, so the same input could be accepted by one path and rejected by the other. Both now use `normalizeArea` from `src/domain/clock.ts`.
- **Environment loading.** Removed obsolete `AUTH_DEV_SANDBOX` and `PILOT_COMMUNITY_ID` assignments from the local `web/.env`; neither is referenced by code.
- Lint, TypeScript, and production build checks pass.
- Remaining verification gap: static checks and these browser runs cannot establish email delivery to real inboxes, concurrency under real parallel load, or recoverability.

## Not implemented / needed before real users arrange rides

- A staffed support route. Reporting storage, reviewer inbox notices, the queue, and blocking exist; notices are in-app only, with no paging or external alert, so a named reviewer must monitor the queue. Reviewer role is granted out-of-band with `npm run db:set-reviewer-role`; a deployment that never runs it has no reviewer. `CONCIERGE_RUNBOOK.md` documents the reviewer workflow and its limits. An operator can now publish a support contact and hours (`/api/support`, shown on the dashboard), but publishing text is not the same as staffing it — someone must still answer, and the app sends no alert.
- Finalized retention schedule (what is kept, for how long, and by whom). **Mechanism now exists:** `npm run db:prune-history` bounds settled trip/request history, evidence and disputes, `db:prune-notifications` bounds read notifications, and `db:prune-idempotency` bounds expired receipts; `db:maintenance` runs all three. What remains is the *policy* and the *schedule*: no window is applied to **closed accounts** (the tombstone) or to **safety reports**, both deliberately, because deleting a tombstone or an incident record is a legal/ethical decision rather than a technical one — a report-linked trip is now explicitly protected from the history prune. Nothing is scheduled by the app; each environment must configure the periodic job.
- Published cancellation, no-show, and dispute terms. A cost-sharing *note* exists (display-only, no payment), but no contribution terms, amount handling, or cost-sharing policy is defined.
- Meeting details are shared as **free text** with no moderation and no per-message report path. A participant can report the *trip* (the existing trip-linked report), and can withdraw their own detail at any time, but there is no way to report or filter text that the other participant wrote in their detail field. Adding message-level reporting was deliberately not done here: a report needs a reviewer action that means something, and the trip report already covers the ride. If a deployment wants to discourage contact exchange specifically, that is a policy decision, not a code one.
- Incident response owner/process and any applicable local legal/insurance/privacy review.
- Production secrets/base URL, deployment and recovery procedures. `npm run health-check` now gives a deployment gate (migrations, schema, enum, guards, scope, policy, invariants) and warns when no reviewer exists, but it is not a monitoring or recovery system.
- No-show *policy*. Evidence is now recorded (`trip_no_show_evidence`) and visible to reviewers, but nothing acts on it: there is no threshold, warning, suspension, or appeal path. Deciding what a pattern of unconfirmed trips should trigger is a product and fairness decision, not an implementation detail. Trip disputes have a manual review path but equally carry no automatic consequence.
- External notifications (email, SMS, push), and delivery outside the in-app inbox. Inbox polling is periodic, not real-time; reviewer notices do not guarantee anyone is online or monitoring. Retention cleanup exists for old **read** notifications (`npm run db:prune-notifications`, default 90 days) but is not scheduled by the app and does not cover unread notices or other tables.
- Apply migrations `0013`–`0032` to any other database environment before relying on notifications, safety-report history, its append-only guards, trip-dispute review (including the reviewer resolution notice), notification retention cleanup, the cost-sharing note, area aliases, area coordinates and distance matching, the support contact, the both-confirmations constraint, and per-trip meeting details (including the trigger that clears them).
- ~~Geographic area matching~~ **Implemented (migration `0026`).** Areas match on normalized text, on operator-declared aliases, and — for areas an operator has explicitly placed — on distance within a configured radius. What remains unaddressed is *route* awareness: the distance is a straight line, so it does not know about roads, barriers, or travel time, and coordinates are entered by hand rather than geocoded.

## Migration and environment notes

- Do not set or rely on `AUTH_DEV_SANDBOX` or `PILOT_COMMUNITY_ID`; the open-marketplace flow no longer uses them.
- `AUTH_ENABLED=true` enables authentication. Before using outside localhost, configure email delivery, valid HTTPS `BETTER_AUTH_URL`, strong `AUTH_SECRET`, database schema, and production privacy/security controls.
- `0006_open_marketplace.sql` adds the automatic marketplace and activates existing app accounts in that scope. `0007_normalized_area_search_index.sql` indexes normalized area comparisons. `0013`–`0015` add in-app ride and safety-report notifications; `0016` adds report audit history; `0017`/`0019` add its append-only UPDATE/DELETE and TRUNCATE guards; `0018` adds the reviewer trip-dispute notification kind. Confirm the target before running migration commands in another environment.
- Never paste `.env.local`, database URLs, auth secrets, or provider keys into chat or commit them.
- Verification scripts that exercise server behaviour should **import the real service modules**, not re-implement their SQL. `scripts/lib/alias-loader.mjs` + `register.mjs` provide the `@/*` alias mapping and are run via `node --experimental-transform-types --import ./scripts/lib/register.mjs`. A script that mirrors production logic verifies the mirror; one that imports it cannot drift.
