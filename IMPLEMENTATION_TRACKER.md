## Product direction

Open email signup. One user account can switch between Rider and Driver. There is no user-facing community, invitation, sponsor, or operator requirement. The database's community/membership structure is retained only as an automatic internal marketplace scope.

## Implemented in the workspace

- Better Auth email magic-link signup/sign-in, with local development links printed to the dev server terminal.
- Signup name and starting Rider/Driver mode.
- Automatic account creation and assignment to the internal marketplace scope.
- Dashboard with Rider and Driver modes and persistent mode switching.
- Visiting `/login` with an active authenticated account redirects to `/dashboard`; signed-out users retain the signup/sign-in flow.
- Dashboard and reviewer-page requests send the account ID that rendered the page; the server rejects a mismatch before running a protected operation. Responses identify the actor, and sign-in completion, sign-out, and account closure broadcast identity changes over `BroadcastChannel` plus a `localStorage` event so personalized state clears immediately. Signals are size-bounded, validated, and deduplicated; older timestamps are ignored. API response checks remain the fallback when both browser transports are unavailable. A 401 redirects to sign-in.
- Mode-gated writes recheck the account's current Rider/Driver mode inside the mutation transaction after acquiring the same per-account lock used by mode changes. This closes the race where a stale Driver tab could publish after the account switched to Rider. A successful mode switch signals other same-account tabs over `BroadcastChannel` plus a `localStorage` event; protected responses also report the current mode so a stale tab detects it on its next request if browser messaging is unavailable. Server authorization remains authoritative.
- Driver commute templates, dated trip publishing, request inbox, accept/decline controls.
- Optional cost-sharing note on a commute (`contributionNote`, ≤160 chars). It is copied onto each trip occurrence at publish time, so editing the commute later does not change what an already published trip advertised. It is display-only: the app parses no amount, stores no structured price, and collects or transfers no money. Search results and the driver's published-trip list show it.
- Driver can edit a saved commute from the dashboard; optimistic version checks prevent stale edits from overwriting newer changes, and publication locks serialize against edits.
- Rider dated trip search, seat request, request list, cancellation control.
- Driver dashboard list of the account's upcoming published dated trips, including status and seat counts.
- Drivers can cancel a future published trip; cancellation and withdrawal of its pending/accepted seat requests happen atomically. A rider's request list exposes the parent trip's status, so a request ended by the driver's cancellation is labelled as that rather than looking identical to the rider's own withdrawal.
- Shared activity view lists the account's driver trips and rider/driver requests regardless of currently selected dashboard mode.
- Users can block/unblock participants from search results or activity; blocks persist, suppress future matches, and are checked transactionally before a new request is created or accepted.
- Area matching ignores capitalization and repeated whitespace; it still requires the same area name unless a reviewer/operator has declared an alias.
- Area aliases (migration `0022_area_aliases.sql`): a reviewer/operator can declare that two spellings mean the same place ("Gulberg III" → "Gulberg"). Search resolves the viewer's area and the trip's area through the same table in one hop, so both directions converge on the canonical name. Nothing is inferred from text similarity or geography. Aliases are unique per alias area, cannot point at themselves, and a chain is rejected at write time so one-hop resolution never disagrees with what the operator sees. Managed at `/moderation/reports`; readable by any active member.
- Driver publish-date form explains the weekly schedule and prevents selecting a date outside the commute's selected weekdays.
- Authenticated service/API boundaries, database migrations, idempotency support in trip mutations, and transaction-based capacity handling in existing domain services.
- Application-wide browser security headers: MIME sniffing and framing disabled, restricted referrer/permissions policy, same-origin opener policy, and production-only HSTS.
- Authenticated API responses (success and error), plus Better Auth API responses, set `Cache-Control: private, no-store`; dashboard requests also bypass browser caches to prevent personalized trip, account, notification, moderation, and session payloads being reused across sessions.
- Idempotency results now replay within their 24-hour window; after expiry, reusing the same actor/operation/key resets the record and executes a fresh operation.
- Dashboard mutations reuse their idempotency key for the exact same account, method, route, and body until a readable successful response; the opaque key and SHA-256 fingerprint survive same-tab reloads in `sessionStorage`, edited payloads get distinct keys, and report text is not persisted in that map. Stale client keys expire after 23 hours, inside the server's 24-hour replay window. This does not deduplicate an independently submitted operation from another tab.
- `npm run db:prune-idempotency` removes at most 500 expired idempotency rows per invocation in a `SKIP LOCKED` transaction.
- `npm run db:audit-retention` reports how much closed-account, report, dispute, trip and notification data exists at a given age (`--as-of-days=<n>`, several allowed). It exists so the retention window can be chosen from real volume rather than guesswork. It runs in a `BEGIN READ ONLY` transaction and deletes nothing; a write attempt inside it is rejected by PostgreSQL, which was verified directly.
- `npm run verify:dispute` exercises the trip-dispute path against a real database (11 checks, self-cleaning): a raised dispute appears in the reviewer queue with confirmation context, a non-disputed request is refused, resolution moves the request to `EXPIRED`/`COMPLETED`, replay is idempotent, a conflicting second resolution is refused, re-reporting reopens the dispute, and the safety-report append-only guard still rejects updates.
- `npm run verify:notifications` exercises the in-app inbox against a real database (8 checks, self-cleaning): a stable event key makes re-inserting the same notice a no-op, the keyset cursor pages without repeating or skipping rows even when many notices share one timestamp, the reviewer dispute-notice kind stores, marking read decrements the unread count by exactly the number of rows changed, and mark-all-read is idempotent.
- `npm run verify:concurrency` drives the real reservation guards through several independent connections at once (8 checks, self-cleaning): many concurrent accepts on a one-seat trip succeed exactly once and the losers get `NO_SEATS_AVAILABLE`, seats never exceed capacity, accepted requests match seats reserved, accepting the same request twice reserves one seat, and a concurrent accept-and-cancel resolves to one coherent outcome. It also includes a negative control that removes the application guard entirely and confirms the database CHECK still refuses to overbook, so the test cannot pass vacuously and a future guard removal is still caught.
- `npm run verify:account-closure` exercises account closure against a real database (11 checks, self-cleaning): closure is refused while the account is on a departed trip, a rider's accepted seat is released with the trip still open, the driver's future trip is cancelled with capacity settled and its riders' requests withdrawn, the account becomes `DEACTIVATED` with its name and auth subject erased and its membership no longer `ACTIVE`, and historical rows survive for other participants. Running it also proved the closure path holds the capacity invariant, not just the status change.
- `npm run verify:support` exercises the support-contact settings against a real database (7 checks, self-cleaning): a plain member fails the operator gate, an operator can set and read back the contact and hours, surrounding whitespace is trimmed, blank input clears to `NULL` rather than an empty string, an over-long value is rejected while a value exactly at the ceiling is accepted, and an unconfigured contact reads as a null pair.
- Reviewer access is bootstrapped deliberately: `npm run db:set-reviewer-role -- <email> <MEMBER|OPERATOR|SAFETY_REVIEWER>` promotes or demotes an existing active account's marketplace membership. It is a separate command, not an HTTP endpoint, so reviewer rights cannot be granted from the web app. Only active accounts can be promoted, and a closed account cannot regain reviewer access. **Writing `npm run verify:reviewer-role` found this command was broken**: its account lookup selected `"user"."userId"`, but that table's primary key is `id` (`userId` exists only on `account`/`session`), so every invocation failed and no reviewer could ever be promoted. Fixed, and the same mistake in the README SQL snippet was corrected.
- Notification rows in the inbox now offer a "View on dashboard" action for ride/trip notices that scrolls to the relevant section and marks the notice read; safety-report notices keep their existing queue link and status action.
- Users can close their own account from the dashboard. A shared per-account advisory lock serializes closure with account-owned mutations; open rider requests are withdrawn and accepted seat reservations released, future driver trips and their requests are cancelled with transactional in-app notices to affected participants, auth identity/credentials/sessions and outstanding magic links are deleted, and historical records survive as an anonymous tombstone.
- Safety reporting UI, reviewer queue at `/moderation/reports` restricted to `OPERATOR`/`SAFETY_REVIEWER`, and reporter-visible status.
- Trip-dispute review: a reported trip moves its request to `DISPUTED` and notifies both the other participant and active reviewers in-app. Reviewers see an open-dispute queue at `/moderation/reports` and resolve it by deciding only whether the trip happened (`COMPLETED` or `EXPIRED`), then both participants receive an outcome notice. Resolution is idempotent, locks the trip before the request in the global order, and penalizes no one automatically. The participant's request row also explains that a reviewer recorded the trip as completed/not completed, so the outcome is visible without relying on the transient notice. The reviewer's dispute row shows each side's confirmation state and whether an unconfirmed-trip record exists, so the decision is made with context rather than the claim alone.
- Reviewer dispute queries and the reviewer-role command were checked against the live schema with `EXPLAIN`. This caught a real defect static checks could not: `$3` was used both as a text comparison and as the `status` column value, which PostgreSQL could not type; it now casts to `ride_request_status`.
- Safety report audit history: submissions and reviewer status changes are recorded as append-only events; row locking serializes simultaneous reviews and same-status retries do not create duplicate events. Pre-feature rows are marked as historical snapshots because earlier transitions cannot be reconstructed. Event history is reviewer-only.
- Reviewer page is server-rendered only for an authenticated account and binds polling, review, and history requests to that account; validated session-change broadcasts clear the sensitive queue immediately, with server response checks as a fallback.
- Moderation queue and unconfirmed-trip evidence refresh on focus and every 30 seconds while visible; monotonic request sequencing prevents a delayed response overwriting newer queue data.
- New safety reports create an in-app inbox notice for each active operator/safety reviewer in the internal marketplace scope; notice creation is atomic with report creation and links to the review queue. Review status changes create reporter-only notices without exposing internal notes.
- Notification inbox uses keyset pagination with a stable `(created_at, id)` cursor; the API fetches at most 51 rows to determine whether another page exists. Older-page loads are single-flight and share a monotonic response sequence with polling/read updates, so stale responses cannot overwrite newer read state or counts. Personalized responses are explicitly non-cacheable.

## Verified behavior this session

- **Trip completion implemented and verified.** Both sides confirm independently; the request completes only when both confirm, and settles to `EXPIRED` if the `completion_window` lapses first. Disputes are recorded in `trip_disputes` and move the request to `DISPUTED`. A request that was never accepted and whose trip has departed is expired rather than left showing an "Accept" control the server will refuse.
- **Capacity-settlement bug found and fixed.** Closing a trip (via confirmation or the expiry sweep) set the status but never released `seats_reserved`, so a finished trip permanently held seats that no request accounted for. That breaks the invariant overbooking protection relies on. Migration `0011` backfills already-closed trips.
- **No-show evidence implemented and verified.** When a completion window lapses, the sweep records which side had confirmed (`RIDER_UNCONFIRMED`, `DRIVER_UNCONFIRMED`, `NEITHER_CONFIRMED`) in `trip_no_show_evidence`, preserving the flags as they stood at expiry. Reviewers see it at `/moderation/reports` under "Unconfirmed trips". It is evidence for a human, never an automatic penalty.
- **In-app notifications implemented.** Seat requests, accept/decline/cancel, trip cancellations, completion confirmations/completion, expiry, disputes, and new safety reports create recipient-scoped inbox entries in the same transaction as the state change. Safety reports notify active operators/reviewers in the internal scope. Stable unique event keys prevent duplicate entries; recipients control read state. The dashboard refreshes on load/action/focus and polls every 30 seconds while visible.
- **Duplicate expiry sweep removed.** `requests.ts` carried its own copy of the sweep, which had drifted: it closed trips without settling capacity and recorded no evidence. It now delegates to the single canonical implementation in `completion.ts`, so the read path cannot diverge again.
- **Trip lock order unified for expiry.** The completion sweep now locks due parent trips in ascending ID order before changing requests, in bounded `SKIP LOCKED` batches of 25. This matches acceptance/cancellation/account-closure lock ordering and avoids concurrent sweepers blocking on the same batch.
- `npm run verify:integrity` is a read-only cross-table integrity check (21 checks) covering the areas added since completion verification: disputes (community match, an open dispute matches a `DISPUTED` request, resolution fields consistent), notifications (recipient/community exist, never addressed to its own actor), safety reports (community match, participants are members, latest audit event matches current status, closed reports are assigned), cost sharing (a published trip never carries a note its unedited commute never had), **area aliases** (community exists, no self-alias, keys are normalized, no cycle), account closure (no live auth subject, no real display name, no ACTIVE membership, no open request), and memberships. Writing it twice exposed **two vacuous checks** (blank/over-long notes, and a blank stored support contact) that could never fire because the schema already forbids those rows; both were removed rather than left to look like coverage. Negative controls confirmed the remaining injected violations (tampered trip note, live auth subject on a closed account, self-addressed notification, open dispute on a non-disputed request, unnormalized alias, alias cycle) are actually detected.
- `npm run verify:area-alias` exercises area-alias resolution against a real database (9 checks, self-cleaning): two spellings do not match before an alias exists, the alias resolves to its canonical area, an unaliased area resolves to itself, a search by the alias finds the canonical trip and vice versa, case/whitespace are still ignored, a second alias for the same area is rejected, an alias pointing at itself is rejected by the schema, and removing the alias restores exact matching.
- `npm run verify:reviewer-role` runs the real `set-reviewer-role` command as a child process (8 checks, self-cleaning): it promotes an active account, switches a reviewer to `OPERATOR`, demotes to `MEMBER`, and refuses an unknown email, a closed account, an invalid role, and missing arguments, without touching an unrelated account. This test found and fixed a bug that made the command fail unconditionally.
- `npm run verify:contribution` exercises the display-only cost-sharing note against a real database (6 checks, self-cleaning): the note is copied to a published trip, editing the commute does not rewrite a trip already published while a later publication uses the current note, an absent note is stored as `NULL` rather than an empty string, and the 160-character ceiling is enforced by a schema CHECK. A note is free text — the app parses no amount and handles no money.
- **Invariant check extended.** `web/scripts/verify-completion.mjs` now also asserts evidence matches its request and outcome, and that settled requests carry no no-show evidence. All 8 pass. `web/scripts/verify-no-show.mjs` exercises the expiry path end to end (9 checks, including that re-running the sweep never duplicates evidence).
- **Overbooking is defended at two layers, and that is now proven.** `npm run verify:concurrency` fires parallel accepts on a one-seat trip through independent connections: exactly one succeeds, the rest get `NO_SEATS_AVAILABLE`, and `seats_reserved` never exceeds `seat_capacity`. Its negative control removes the application guard on purpose and shows the database `CHECK` still refuses the increment — so the test cannot pass vacuously, and a future removal of the app guard is still caught. A concurrent accept and trip-cancel resolves to a single coherent outcome with no accepted request left on a cancelled trip.

- **Published-trips race fixed.** The dashboard previously issued two overlapping loads; a slow earlier response could overwrite newer data, so a freshly published trip did not appear. The loader is now a single guarded function with a monotonic sequence number, and the initial load is deferred out of the effect body.
- **Area normalization unified.** Template creation previously validated raw length while search validated normalized length, so the same input could be accepted by one path and rejected by the other. Both now use `normalizeArea` from `src/domain/clock.ts`.
- **Environment loading.** Removed obsolete `AUTH_DEV_SANDBOX` and `PILOT_COMMUNITY_ID` assignments from the local `web/.env`; neither is referenced by code.
- Lint, TypeScript, and production build checks pass.
- Remaining verification gap: static checks and these browser runs cannot establish email delivery to real inboxes, concurrency under real parallel load, or recoverability.

## Not implemented / needed before real users arrange rides

- A staffed support route. Reporting storage, reviewer inbox notices, the queue, and blocking exist; notices are in-app only, with no paging or external alert, so a named reviewer must monitor the queue. Reviewer role is granted out-of-band with `npm run db:set-reviewer-role`; a deployment that never runs it has no reviewer. `CONCIERGE_RUNBOOK.md` documents the reviewer workflow and its limits. An operator can now publish a support contact and hours (`/api/support`, shown on the dashboard), but publishing text is not the same as staffing it — someone must still answer, and the app sends no alert.
- Finalized retention schedule (what is kept, for how long, and by whom). Account closure exists, and `npm run db:audit-retention` reports volumes by age to inform the choice, but no window is applied to closed accounts, reports, or trips; only old **read** notifications are prunable today.
- Published cancellation, no-show, and dispute terms. A cost-sharing *note* exists (display-only, no payment), but no contribution terms, amount handling, or cost-sharing policy is defined.
- Incident response owner/process and any applicable local legal/insurance/privacy review.
- Production sender/domain, production secrets/base URL, deployment and recovery procedures.
- No-show *policy*. Evidence is now recorded (`trip_no_show_evidence`) and visible to reviewers, but nothing acts on it: there is no threshold, warning, suspension, or appeal path. Deciding what a pattern of unconfirmed trips should trigger is a product and fairness decision, not an implementation detail. Trip disputes have a manual review path but equally carry no automatic consequence.
- External notifications (email, SMS, push), and delivery outside the in-app inbox. Inbox polling is periodic, not real-time; reviewer notices do not guarantee anyone is online or monitoring. Retention cleanup exists for old **read** notifications (`npm run db:prune-notifications`, default 90 days) but is not scheduled by the app and does not cover unread notices or other tables.
- Apply migrations `0013`–`0023` to any other database environment before relying on notifications, safety-report history, its append-only guards, trip-dispute review, notification retention cleanup, the cost-sharing note, area aliases, and the support contact there.
- Geographic area matching. Areas still match on normalized text; equivalence is available only through explicit operator-declared aliases, not geographic proximity or inferred similarity.
